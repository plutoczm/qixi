# 寻栖实习准备笔记

## 一分钟项目介绍

寻栖是一个 Windows 本机酒店参考查询工具。用户给出中国大陆目的地、日期、入住条件和预算，页面用道旅、途牛、飞猪找候选，再显式核对房型、地图路线和当前打车估价。前端是 React、TypeScript 和 Vite，后端是 FastAPI，SQLite 只保存需要延续的最小会话状态。重点是把来源结果、确定性规则、人为确认和未知条件分开，让用户可以追到每条推荐的依据。

- 请求路径可从 [网页路由和表单](../frontend/src/App.tsx) 追到 [FastAPI 装配](../backend/stay_agent/main.py)。
- 并行来源看 [并行搜索](../backend/stay_agent/parallel_search.py)，推荐规则看 [自动推荐](../frontend/src/parallelRecommendations.ts)。
- 交通看 [交通服务](../backend/stay_agent/travel.py) 和 [卡片交通](../frontend/src/HotelTransport.tsx)，启动看 [托盘入口](../launcher/XunqiTray.cs)。

## 实际解决过的问题

| 问题 | 发现与解决 | 面试时要说清楚的边界 |
| --- | --- | --- |
| 真实接口返回数据，却被应用判为失败 | 途牛搜索响应有 `success`，房型详情可以省略该字段，且结果可能在 MCP 文本包裹中。按接口分别验业务标记，结合原搜索成员、酒店 ID 与名称核对详情。地址缺失和地址显式冲突分别处理。 | 能投影真实房型仍不等于入住组合和含费实付已经核实。 |
| 三家报价看上去可以直接比价 | 来源计价口径、入住回显和覆盖不一致。并行只负责召回，各自保留原会话。飞猪只提供名字和展示线索，不能进入报价或库存语义。 | 每家独立限额和错误分类，单家失败时保留其余结果。跨来源价格没有被硬换成同款价格。 |
| 推荐第一屏不符合用户直觉 | 对抗式样本发现，¥200 查询的五条 ¥900 展示价能挤掉 ¥120，120 米和 1,499 米同分，相同店名地址重复占位，身份冲突过五分钟又回来。用四个反例做回归，将展示价限定为一晚一房预算线索，同档用核实步行距离排序，仅合并展示名额，并延续同轮冲突直到有有效新证据。 | 这是四个可复现规则问题的改善，节省多少人工核对动作还缺真实样本统计。 |
| 地图和车费找到了同名或不同名地点 | 丽呈铂锐的门址在两个来源文字不同，餐厅也有不同门店叫法。首轮停在身份核对，后续让用户核对出发点与酒店两端，使确认只绑定到当前卡片的两份有效观察。两家各自使用自己的位置数据。 | 真实网页一次样本为步行约 32 分钟、驾车约 13 分钟、当时快车估价 ¥16。驾车时间不含候车，估价不代表未来价格。 |
| 用户改条件，之前查价或模型回复迟到 | 请求带会话、revision 和操作编号。后端用提交屏障拒绝旧结果，前端检查当前代次及来源。显式取消保留已提交条件，模型只提议条件补丁，用户确认后才会填表和提交。 | 可阻止旧结果写回当前页面，无法保证第三方已经停止处理或计费。 |
| 地图地点有效期和网络超时混在一起 | 地点上下文有固定 120 秒。每次用户触发的地图步骤有独立截止时间，同时受原上下文剩余时限约束，避免把过期响应误当当前路线。 | 分清远端超时、上下文过期和来源限流，不能自动刷新来绕过门禁。 |
| 用户关了窗口，以为服务结束 | 桌面独立 EXE 管理单实例和本机服务，健康后开启 Edge 应用窗。普通关窗保留托盘，托盘退出后请求 Uvicorn 正常结束并释放端口。 | EXE 使用本机项目和 Python 环境。它可以一键启动，跨机免安装分发并未交付。 |
| 销售看起来有房、显示价也看起来很低 | 用确定性规则区分参考价、明确资格和未知字段。缺足量库存、完整入住回显、逐夜费用或押金证据时保持参考状态。取消外部点评接入及完整可订范围，用户去住宿平台核价订房。 | 参考查询的验收可以完成。证明最终实时可订仍需供应商给出授权字段及相同请求的完整证据。 |

## 准备追问

1. 并行搜索遇到单家超时怎么办？讲清每来源请求预算、共同截止时间、部分结果和提交屏障。
2. 怎么证明同一家门店？讲完整名址、城市和双向唯一，还要说明人工确认的作用域和撤销行为。
3. 怎样验证功能？分开讲规则回归、模拟浏览器和真实接口三个层次。用四个推荐反例与一组真实交通样本说明证据边界。
4. 为什么不做实时可订？解释条件和收费口径需要什么接口证据，以及本机个人参考工具已经解决的用户问题。
